## 3. Measured host RAM budget — the binding constraint

The accepted configuration already runs **at its host cap**. This is the central
RC0 finding.

| Item | Measured | Evidence |
|---|---:|---|
| cgroup `MemoryMax` | 56.00 GiB (60,129,542,144 B) | `host/cgroup_memory.max` |
| cgroup `memory.current` | 55.77 GiB (59,887,382,528 B) | `host/cgroup_memory.current` |
| `memory.events max` | **833** (cap hit 833 times → repeated reclaim) | `host/cgroup_memory.events` |
| Pinned/shmem host expert memory | **~25.25 GiB** — 135 × `/dev/zero (deleted)` mappings in scheduler smaps, non-reclaimable | `host/scheduler_smaps_rollup.txt`, mapping sum |
| PLE file page cache | **~25.3 GiB resident** of a 47.7 GiB ext4 file, reclaimable | `cgroup_memory.stat` (`active_file`+`inactive_file`), `model/ple.json` |
| Anonymous | ~5.1 GiB | `cgroup_memory.stat anon` |

Reconciliation: cgroup v2 `file` (50.5 GiB) = `shmem` 25.25 GiB (pinned experts)
+ ~25.3 GiB non-shmem page cache (PLE + weight reads). `memory.current` =
anon 5.1 + file 50.5 + kernel 0.15 = 55.77 GiB.

Consequences for a RAM tier:

- **There is no free host RAM at the current settings.** A snapshot cache must be
  carved from one of: (a) pinned expert memory (`--cpu-offload-gb 19`, the
  ~25.25 GiB non-reclaimable block), (b) PLE page cache (reclaimable, but reclaim
  makes PLE reads hit the ext4 SSD), or (c) the host's remaining reclaimable
  headroom by raising `MemoryMax` above 56 GiB.
- Under `MemTotal` 62.8 GiB, system-wide `MemAvailable` was ~29 GiB, but that is
  dominated by the reclaimable PLE cache; other workloads (t3/opencode/codex/
  docker) use a few GiB. Raising the scope cap is possible but must not starve
  them.
- The PLE table is `np.memmap(..., mode="r")` + `MADV_RANDOM` + parallel `pread`
  (`qwen4_exp.py:781-872`), explicitly "no pinned host memory"; its RSS in the
  scheduler is only ~6 MB, so its real cost is page cache, i.e. reclaimable and a
  direct competitor to a RAM cache working set.

## 6. Tiered-KV precision contract (design gate)

The `int8ring_int4` pool is a dual-write tier: `_stamp_ring_owner` writes
`owner[slot & 8191] = slot`; the int8-g64 row is written only if the stamping
slot still owns the ring row, and **every** token is also written to the int4
full-context row (`tiered_kv_pool.py:114-160`, `sparse_attn.py:958-1071`).
Readers take the int8 row iff `owner[slot & mask] == slot`, else the int4 row
(`sparse_attn.py:1130-1302`). The ring is **not a `KvBufferDesc`**, lives outside
the lazy VMM owner, and is never relocated by `move_kv_cache`
(`tiered_kv_pool.py:11-14,97-99`).

Therefore an exact restore must:

1. Preserve the packed INT8 row + fp16 scale for every slot with a valid owner
   entry at snapshot time, plus its **logical token association** (slot id), not
   just its physical ring row.
2. Preserve the ring-owner map (physical slot → owning slot) or an equivalent
   per-slot precision flag, so restore reproduces which tokens were read at INT8
   vs INT4.
3. Resolve destination ring-row collisions: restoring two conversations whose
   former slots map to the same destination ring row cannot both keep INT8. The
   plan's gate is to choose a request-local ring or equivalent remap and validate
   it; **reconstructing INT8 from INT4 is forbidden**.
4. Keep the int4 rows + scales and all recurrent/PLE state at the same checkpoint
   boundary; a hit is only complete when all components exist.

RC0 records this as **unresolved and load-bearing**: no existing abstraction
stores the ring precision map, and the ring is not addressable by any host pool.
RC1/RC2 must settle it before any exactness claim.

## 9. Feasibility verdict and explicit budgets

**Feasible, but only by re-partitioning the existing budget; it does not fit on
top of the accepted settings.** The binding limit is host RAM (cgroup at cap,
56 GiB, 833 max-hits) and VRAM (1.6 GiB idle, 40–80 MiB at 257K accepted).

Proposed explicit budgets to evaluate in RC3/RC4 (not yet allocated):

| Budget | Value | Source |
|---|---:|---|
| RAM snapshot tier (retained conversations) | 6–10 GiB | from PLE page cache / raised cap, not from pinned experts |
| Pinned staging (reusable) | 0.5–1.0 GiB | existing `SGLANG_MOE_ELASTIC_PIN_MB=512` + headroom; never pin all RAM |
| GPU hot tier | ~1–3 GiB | from reduced S184 residency / active-context reserve |
| Recurrent-state slots | ≥4 (extra-buffer) + 1 ckpt reserve | `common.py:25-29`, `kv_cache_configurator.py:1874-1903` |
| Active context reserve | keep 262,144 target; generation reserve measured | smoke at 257,456 + 512 gen |

At 1.06 GiB per 120K conversation, 6–10 GiB holds ~6–9 retained 120K
conversations, or ~3–5 near-262K conversations. That is the working hypothesis to
test; it is not yet measured against PLE/offload pressure.

## 10. Test protocol (fixed here, executed in RC1–RC4)

Correctness (byte identity before numerics):
- Component round trips for int4 payload+scales, QSA compressed pool, ring
  rows+owner map, GDN conv+temporal, PLE short-conv+ngram — byte-equal.
- Incremental decode with state updates, not bulk teacher-forced suffixes; bound
  the measured 8,192-ring baseline drift (TG0: max |dlogprob| 0.128–0.315).
- Boundaries: QSA page 64, 4,608 chunk, 8,192 ring, 256 tracking interval,
  partial final chunk.
- Physical-slot remap, source-slot reuse, shared-prefix eviction with a branch
  alive, metadata mismatch, aborts, allocation failure, interrupted transfer,
  sustained churn, leak checks.

Isolation: A→B→A after GPU eviction; divergent branches; repeated/appended
requests; two conversations whose recovered slots collide on a ring row.

Agentic performance: exact-token traces (shared repo/system prefix, tool-result
appends, fork-and-return, interleaved conversations; 8K/32K/120K and near-limit),
three arms (frozen no-cache, GPU-only hybrid, RAM-backed), ≥5 traces/scenario with
a predeclared warmup, confirmation across boots. Record matched/recomputed tokens,
TTFT, restore/spill and queue time, TG inter-token latency, **total trace wall
time**, bytes moved, peak/sample RAM+VRAM, failures. Acceptance is the agentic
crossover: saved prefix recomputation must exceed restore/checkpoint overhead
plus extra suffix-prefill/generation time. TG and cold-prefill costs are reported,
not vetoed (plan §"Promotion").

## 11. What RC0 cannot conclude / open items

- Exact QSA pending-ring and RoPE sizing need a runtime probe (`req_to_token`
  slot count) in RC1; it is small but not yet measured.
- The lazy VMM owner logged 96 MB for 8,192 tokens (~12.3 KB/token) versus the
  nominal 6.9 KB/token of payload+scales; the ~1.8× factor is page/desc rounding
  and must be measured before sizing the host tier.
- `memory.stat` `anon` (5.1 GiB) does not equal `active_anon + inactive_anon`
  (30.4 GiB) on this kernel; only the reconciled `file`/`shmem` split is used.
- No cache behavior, no restore, and no agentic latency was measured. RC0 is a
  budget/contract gate, not a hit-rate or speed claim.
