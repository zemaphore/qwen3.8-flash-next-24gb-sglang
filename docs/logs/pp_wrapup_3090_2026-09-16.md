# PP campaign wrap-up: long-prompt validation and final characterization (RTX 3090)

Date: 2026-09-16 UTC

Base commit: `a50c32a` (PP15c, accepted stack)

Decision: **close the prompt-processing optimization campaign.** The accepted
defaults stay as they are; the default-off research patches stay default-off. No
new optimization sweep was started. The accepted stack was exercised on long
prompts that reach the PP15 MoE config and the PP14 prefetch floor, and
characterized on canonical, held-out, and long-context workloads. Numerical
equivalence remains qualified as detailed in the closure review below.

## 1. Scope

The prior exactness claims rested on two short-prompt oracles
(`tools/logprob_diff.py`, three prompts of a few hundred tokens each) and on
`greedy_diff.py`, which is explicitly not an oracle because this server is not
bitwise reproducible run to run. None of those prompts reaches 2,048 tokens, so
none exercised the PP14 prefetch path (gated at 2,048) or the PP15 `M=4565` INT2
MoE config (which only applies to the 4,565/4,608-token chunks). This wrap-up
adds a teacher-forced logprob oracle over fixed long prompts and reports the
run-to-run variability that any comparison must be read against.

Default-off experiments (full-table gather, first-layer prefetch, QSA host
lens) are **not** promoted or re-validated for promotion here. Their existing
short-oracle results stand; the long-prompt validation distinguishes them from
the accepted paths and does not claim their changed paths are exercised by the
defaults.

## 2. Long-prompt teacher-forced logprob validation

Tool: `tools/long_logprob_oracle.py`. Fixed prompts, actual server token counts
confirmed by the tokenizer and by the server:

| Prompt | Construction | Actual prompt tokens | Forced suffix |
|---|---|---:|---:|
| canonical | `bench_agentic` base prompt; scoring suffix crosses chunk boundary | 4,565 | 150 |
| long-2chunk | held-out code corpus, spans two 4,608 chunks + tail | 11,196 | 150 |
| long-4chunk | held-out code corpus, spans four 4,608 chunks + tail | 20,496 | 150 |

The continuation is a fixed token-id suffix (`tools/greedy/oa.json[2][:150]`), so
every arm scores identical tokens. Long prompts are tokenized locally and only
the short forced suffix is scored server-side; asking the server for full-prompt
logprobs OOMs its logprob processor at these lengths (retained as a tooling
finding, not a serving result).

### Repeat-run variability (accepted server, unchanged configuration)

Three runs on one accepted server, same boot:

| Comparison | canonical max / mean | long-2chunk max / mean | long-4chunk max / mean |
|---|---:|---:|---:|
| run1 vs run2 | 0.828 / 0.040 | 0.716 / 0.048 | 0.969 / 0.059 |
| run1 vs run3 | 0.812 / 0.041 | 1.374 / 0.055 | **1.781** / 0.055 |
| overall envelope | | | **1.781 max, 0.050 mean** |

The largest deltas sit at forced-token indices 0-6, where the fixed continuation
is a very unlikely suffix token (logprob -6 to -8). Those positions are
genuinely non-reproducible run to run. **Long-prompt logprobs are therefore not
bit-exact, and no long-prompt comparison is reported as "exact".**

### PP15 MoE config (accepted) vs pre-PP15 MoE config

One accepted-stack server and one pre-PP15 server (`M=4565` entries removed from
E=384/E=432), everything else identical:

| Prompt | max \|dlogprob\| | mean | vs accepted envelope |
|---|---:|---:|---|
| canonical (4,565) | 1.410 | 0.046 | inside |
| long-2chunk (11,196) | 0.483 | 0.043 | inside |
| long-4chunk (20,496) | 0.730 | 0.049 | inside |
| **overall** | **1.410** | **0.046** | inside (envelope max 1.781) |

The MoE comparison's global maximum is below the observed baseline global
maximum. This is reassuring but is not a statistical equivalence test: the
canonical delta exceeds its own recorded baseline maxima, and per-token JSON
was not retained for this control. Numerical equivalence is not established.

### PP14 prefetch on vs off at qualifying lengths

Two prefetch-off runs against the accepted run1:

| Run | canonical max / mean | long-2chunk max / mean | long-4chunk max / mean |
|---|---:|---:|---:|
| prefetch-off run1 | 0.980 / 0.042 | 2.797 / 0.059 | 0.846 / 0.049 |
| prefetch-off run2 | 0.890 / 0.046 | 0.759 / 0.048 | 0.957 / 0.054 |

The prefetch-off run1 `long-2chunk` value of 2.797 is a single early forced-token
outlier (index 6, an unlikely suffix token); the same configuration re-run gives
0.759 at that index, and the accepted configuration's own run-to-run envelope
reaches 1.781. Every prompt length here qualifies for prefetch (>= 2,048). The
2.797 outlier exceeds the observed baseline envelope. Its cause remains
unresolved; a quieter repeat does not establish numerical equivalence or prove
that the first observation was harmless noise.

### Path activation

`activation-evidence.txt` records the accepted server taking the intended paths:

- PP14: `MoE cross-layer cold-row prefetch active at >=2048 tokens` and the four
  cache allocations (w13 419 MB, w2 210 MB, scales 26/13 MB).
- PP15: the canonical 4,565-token extend resolves to the E=432 bucket (5,628
  `Using nearest MoE expert-count config E=432` lines in the run), and with the
  selection rule `min(configs.keys(), key=abs(x-M))` at
  `fused_moe_triton_config.py:348` the 4,565/4,608 chunk picks the `4565` key and
  the ~2-3k tails pick `1024`.
- The pre-PP15 config files have keys `[128, 512, 1024]` only.

## 3. Final performance characterization (accepted defaults)

### Canonical and held-out capture

`tools/capture_pp5b_arm.py` on the accepted stack (one discarded warmup per
corpus, measured samples retained, raw outputs and `nvidia-smi` samples kept):

| Corpus | Actual prompt tokens | Measured PP tok/s | Decode tok/s |
|---|---:|---:|---:|
| canonical (one extend) | 4,565 | **2666.8 +/- 12.5** (n=5) | 41.4 |
| held-out `scripts/phase1.py` | 3,810 | 2590.0 +/- 6.9 (n=3) | 38.0 |
| held-out `scripts/05_quantize.py` | 3,866 | 2581.3 +/- 13.6 (n=3) | 33.8 |

Both short oracles are unchanged (`m4_3090_untuned` 0.000000/0.000000; `lp2`
0.168757/0.011632). The 2666.8 canonical mean is a different session from the
PP15 acceptance mean of 2687.4 +/- 48.3 and is not pooled with it.

### Depth sweep

`tools/depth_sweep.py`, one request per depth, `--decode-tokens 16`, chunked
prefill 4,608, single accepted-stack boot. Requested depth is a chars-per-token
label; the table reports the actual server token count:

| Requested | Actual prompt tokens | Prefill s | Prefill tok/s | Decode tok/s | Min free VRAM | Status |
|---:|---:|---:|---:|---:|---:|---|
| 8,192 | 10,573 | 7.53 | 1,404 | 38.2 | 1,602 MiB | ok |
| 32,768 | 42,732 | 25.19 | 1,697 | 36.0 | 1,414 MiB | ok |
| 65,536 | 85,765 | 43.72 | 1,962 | 34.6 | 1,126 MiB | ok |
| 131,072 | 171,604 | 93.71 | 1,831 | 40.0 | **40 MiB** | ok |
| 163,840 | 214,031 | 136.10 | 1,573 | 35.6 | 58 MiB | ok |
| 180,224 | 235,101 | 152.02 | 1,547 | 38.5 | 44 MiB | ok |
| 196,608 | 257,456 | 166.81 | 1,543 | 39.9 | 80 MiB | ok |
| 204,800 | 267,001 (rejected) | - | - | - | - | input longer than context |
| 245,760 | 320,945 (rejected) | - | - | - | - | input longer than context |
| 262,144 | 343,026 (rejected) | - | - | - | - | input longer than context |

The largest accepted prompt was **257,456 tokens** (196,608 requested) at 1,543
tok/s prefill, 39.9 tok/s decode, and 80 MiB minimum free VRAM. The model context
is 262,144 tokens; the sizes above it are rejected by the context check, which is
the documented ceiling, not a hardware retraction. No OOM, retraction, or CUDA
fault occurred in any accepted depth. The 40-80 MiB headroom near the limit is
real but small: treat long-context requests as running with little margin.

## 5. Conclusion and limitations

- The campaign is complete and the accepted stack is frozen. From here the
  remaining levers are **configuration and scheduling changes showing
  diminishing returns**, not a proven hardware ceiling. No configuration or
  scheduling change on the table now clears a materiality gate.
- 91.5% GPU-compute time coverage in the PP15 profile means 91.5% of the measured
  span had some GPU engine active. It is **not** 91.5% hardware efficiency and
  must not be quoted as utilization, throughput efficiency, or a ceiling.
- The full-table gather (+0.9%, within noise), the first-layer prefetch (+0.3%
  pooled, within noise), and the QSA host-length metadata (no pooled effect)
  show **no demonstrated material benefit**. They remain default-off research
  patches.
- Exactness: the short oracles are reproduced exactly. Long-prompt teacher-forced
  logprobs are **not** bit-exact; run-to-run max drift reaches 1.78 on the early
  forced tokens with mean ~0.05. One PP14 control comparison exceeds that
  envelope at 2.797. Neither change has a conclusive equivalence result.
- The depth sweep ceiling (257,456 accepted tokens, min free 80 MiB) and the
  earlier long-prompt passes are single-boot observations; the sweep is
  reproducible but not repeated across boots.

## 7. Evidence

### Closure review (reviewed through `52b2238`)

The optimization campaign is closed with frozen defaults, while the following
validation limitations remain explicit. Raw evidence and its original summary
are preserved; this review supersedes the summary JSON's equivalence wording.

- The oracle appends 150 input tokens and generates one token. The canonical
  scoring request therefore contains 4,715 input tokens, crossing the 4,608
  chunk boundary. It exercises the new config via the 4,608 chunk, but is not a
  one-extend M=4565 numerical test. It does not test sustained decode.
- `stats()` accepts truncated arrays and does not require identical prompt IDs,
  complete continuations, or finite values. Its `check` threshold of 0.05 is
  incompatible with the measured unchanged-server drift. TG0 must harden the
  harness and define a baseline-derived decision policy before using it as a
  gate; merely raising the threshold to admit an outlier is insufficient.
- Early unlikely suffix tokens identify where drift occurs, not why. The 2.797
  prefetch delta remains unresolved. TG0 should preserve per-token comparisons
  and use matched repetitions and path/state checks to characterize it.
- The depth sweep has one request per size and 16 generated tokens. It is a
  capacity/PP characterization, not a reliable TG latency distribution. Input
  lengths were estimated from characters; actual counts are retained. It does
  not establish a successful request at exactly the context boundary.
- Reported free VRAM is sampled, not a guaranteed allocation reserve. Preserve
  the 262,144 context setting and test actual near-limit operation after future
  changes; do not infer safety for new buffers from the successful single boot.
