# PP6 — complete GDN pipeline profile at M=2048: tuning premise measured false

Date: 2026-09-15. Host: RTX 3090. Stack: accepted PP7 state (bulk pread +
128 MiB recent-row cache, 2,048-byte gather tile, host-row DMA staging,
2,048-token chunks, S184), server `sglang-1789491753.scope`, port 30001,
`SGLANG_MOE_GATHER_DMA=1`. No code change, no restart; profile taken through
the live `/start_profile` endpoint.

## What was asked

PP6 planned to tune or fuse the 36 Triton GDN layers, on the premise that they
"contain more untuned PP time than fused MoE", and to recheck whether GDN/QSA
dual-stream overlap clears PP4's 5% gate now that staging is DMA-bound at
~12.5 ms/layer.

## Method

One warmed population request (1109 tok/s, matching the accepted 1111.8
baseline), then a stage-filtered torch-profiler capture:

```bash
curl -s -X POST http://127.0.0.1:30001/start_profile -H 'Content-Type: application/json' \
  -d '{"output_dir":"/tmp/pp6-profile","profile_by_stage":true,"num_steps":3,"activities":["CPU","GPU"]}'
SGLANG_URL=http://127.0.0.1:30001/generate python3 tools/bench_agentic.py --tokens 4096 --decode-tokens 256
```

The 4,565-token prompt runs as two full 2,048-token extends plus the padded
469-token tail; profiling auto-flushed at the first decode step. Trace:
`/tmp/pp6-profile/1789493729.4675837-TP-0-EXTEND.trace.json.gz` (44 MB gz),
analyzed with `tools/chrome_trace_summary.py --within "step[EXTEND"` plus a
category pass. `step[...]` spans appear twice per step (CPU `user_annotation`
plus `gpu_user_annotation` copy); the span-union logic treats them as one.

## CPU-side attribution (span 2 wall = 1,773 ms)

- `_run_qwen4_exp_mlp` (48 MoE layers): 1,382 ms = 28.8 ms/layer, of which
  `expert_stream.gather` 1,224.6 ms and `_gather_dma` 829.6 ms.
- `_unique2` 391.3 ms (49 calls, 8.0 ms each), `aten::item` 381.7 ms,
  `cudaStreamSynchronize` 380.6 ms — the staging sync chain.
- DMA submission machinery: `aten::select` 119,809 calls / 238.7 ms,
  `aten::copy_` 357.0 ms, `cudaMemcpyAsync` 49,874 calls / 209.9 ms.
- GDN-layer attention CPU wall: ~7.1 ms/layer x 36 = ~256 ms (14%), all async
  submission; QSA layers ~10.4 ms/layer x 12.

The CPU thread is the serializer: SMs are idle ~63% of the span, the copy
engine ~49%, and the CPU is fully occupied by the staging path.

## Verdict

1. **PP6 tuning/fusion: REJECTED on profile evidence, no A/B needed.** The
   premise "36 Triton GDN layers contain more untuned PP time than fused MoE"
   is false on the PP7 stack: GDN is 40.2 ms/chunk versus 238.0 ms fused MoE.
   Halving every GDN kernel would move end-to-end PP by ~1.1%; the 5% gate is
   unreachable. GDN at M=2048 is well-tuned relative to everything around it.
2. **GDN/QSA dual-stream overlap recheck: still below the gate.** GDN+QSA =
   92.1 ms/chunk = 5.2% of span wall nominally, but the span is CPU-bound on
   the staging path, and same-layer structure forbids overlap (layer L+1's
   staging needs layer L+1's router, which needs layer L+1's attention).
   PP4's dual-stream A/B measured flat under the same constraint; the DMA
   change does not alter the CPU serialization.
3. The remaining PP walls, in order: (a) per-layer-chunk fixed staging cost
   (~12-18 ms/layer; the 469-token tail still pays 664 of its 1,107 ms for
   staging), (b) the CPU staging path (unique2 + item/tolist syncs + 50k
   per-row copy submissions = 78% of CPU wall), (c) INT2 fused MoE 238
   ms/chunk, (d) Marlin 172 ms/chunk.

## Consequences for the queue

- PP6 closed REJECTED; the queue's GDN bullet is retired.
- Opened **PP11 (NEXT)**: staging-path CPU/sync elimination — precompute row
  views at resize, batch the per-row copies, and remove the tolist/item sync
  from the staging critical path. Ceiling if fully successful: span wall
  approaches max(DMA 875, SM 652) ~ 0.9 s/chunk, i.e. roughly 2x current PP.
- The 469-token tail pays nearly a full chunk of fixed staging cost; a later
  item may merge or special-case the tail, but it is ~10% of prompt tokens.
- Decode traces (3 decode steps) landed in
  `/tmp/pp6-profile/1789493729.4675837-TP-0-DECODE.trace.json.gz`; decode is
  DECODE_PERF_PLAN scope, not analyzed here.

Note: the profiled bench reported decode 6.1 tok/s because trace serialization
of the 44 MB extend trace stalled the scheduler ~31 s mid-request; prefill
numbers under the profiler (1009 tok/s) are overhead-inflated and excluded per
protocol. The warmed non-profiled baseline for this session is 1109 tok/s.

Server left running unchanged: `sglang-1789491753.scope`, DMA=1.
