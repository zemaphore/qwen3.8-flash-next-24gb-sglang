## 1. Scope and configuration snapshot

This is the TG0 stage of [TG_PERF_PLAN_3090.md](TG_PERF_PLAN_3090.md): a
single-stream TG baseline, a measured decode cost breakdown, and a validation
harness suitable for future changes.  No placement tuning, kernel optimization,
speculation, quantization, or flag sweep was run.  TG1/TG2 were not started.

The accepted server was launched unchanged with `/root/quant/serve-3090.sh`
(SHA-256 `11013fb6...`; boot-1 argv/env in
`raw/tg0_3090_2026-09-16/manifest/server-accepted.json`).  Effective settings
include `--max-running-requests 1`, `--chunked-prefill-size 4608`,
`--cuda-graph-backend-decode breakable`, `--kv-cache-dtype int8ring_int4`,
`--attention-backend triton`, `SGLANG_KV_TIERS_W=8192`, S184 presence placement
(`assets/expert_presence_code.pt`, SHA-256 `73d8f0df...`), PP14 cross-layer
prefetch at `>=2048` tokens, PP15 `M=4565` MoE entries, and the accepted PLE
bulk-pread/recent-cache/DMA settings.  Software: Python 3.12.3, torch
2.13.0+cu130, Triton 3.7.1, transformers 5.12.1, sglang `0.5.20.dev1+g73a255206`,
CUDA 13.0 (nvcc 13.3), driver 580.178.04, RTX 3090 sm_86 (full manifest in
`raw/tg0_3090_2026-09-16/manifest/`).

Verified before measurement:

* **Breakable decode graph replay.**  The server log records
  `Capture target decode CUDA graph ... bs=[1]` and the decode profile shows the
  per-token broken-graph span sequence (`step[DECODE bs=1]`, 15 segments/token).
  No fallback/`cuda_graph: False` decode step was observed.
* **In-place expert GEMV.**  Decode (`hidden_states.shape[0] <= 16`,
  `weight_bits == 2`, `SGLANG_MOE_GEMV=1`) dispatches to
  `_apply_gemv` → `moe_gemv_int2_tab`, which indexes a per-expert pointer table
  with the original ids ("no gather, no staging, no renumbering";
  `expert_gemv.py`).  Both decode-profile traces contain exactly the
  `_moe_gemv_int2_tab` kernel (96 launches = 48 layers × gate/up + down per
  token).  Historical Blackwell figures were not used as 3090 evidence.

## 2. Method

Prompts were frozen and hashed before timing: prose (README/CHANGELOG/WRITEUP/
MODELCARD/HISTORY/CAMPAIGN/TIMELINE), reasoning (DECODE/ELASTIC/KV/SPEC/PP/TG
plans) and code (serving patch + `scripts/` + `tools/`) corpora, sliced to exact
**2,048 / 32,768 / 131,072** token ids by the model tokenizer
(`tools/tg_prompts.py`, `raw/.../prompts/prompts.json`).  Cell repetition is
recorded explicitly: prose repeats ×2 at 128K, reasoning ×1, code ×0.

`tools/tg_baseline.py` sends `input_ids`, greedy (`temperature=0`,
`ignore_eos`), exactly 512 generated tokens per request, one request at a time.
Per predeclared policy each cell is one excluded warmup then five measured
requests, in a balanced order that rotates class order per depth
(`prose/reasoning/code` at 2K, `code/prose/reasoning` at 32K,
`reasoning/code/prose` at 128K).  No cache was flushed and no clock was changed.
TG is `(last_count-first_count)/(last_time-first_time)` on `time.monotonic()`
events, excluding TTFT.  `stream_interval=1` gave one event per token, so
median/p95 inter-token intervals are real token-latency observations
(`individual_token_timing = true` for all 45 measured samples).  Clocks, power,
temperature and free VRAM were sampled every 250 ms; every raw sample, output
text and timestamp list is retained under `raw/.../boot1/` and `boot2/`.

## 4. Decode cost breakdown

Three warmed decode windows were captured with the stock `/start_profile`
endpoint (`profile_by_stage`, no stack, no recorded shapes) and analysed with
`tools/tg_profile.py`.  A decode token appears as ~15 breakable-graph segments,
so attribution is per token over a 20-token window.  Values are ms/token.

| Family (kernels) | 2K | 32K | 128K |
|---|---:|---:|---:|
| expert GEMV (`_moe_gemv_int2_tab`, in-place host/device rows) | **14.60** | **12.96** | **17.13** |
| dense / Marlin / cuBLAS (`Marlin`, `gemvx`, `cutlass`) | 12.68 | 12.29 | 13.48 |
| PLE / graph-boundary (`_hc_mix_persistent`, `hc_combine`) | 2.45 | 2.48 | 2.46 |
| router + sampling + top-k | 0.81 | 0.91 | 1.07 |
| other elementwise / fill / reduce | 0.88 | 0.95 | 1.06 |
| GDN (`gated_delta`, `conv1d`, `qkvzba`) | 0.55 | 0.56 | 0.56 |
| attention / QSA / KV tiers | 0.51 | 0.52 | 0.52 |
| expert HtoD DMA (separate) | 0.08 | 0.08 | 0.08 |
| **summed kernel time** | 32.5 | 30.8 | 36.4 |
| **kernel-union (engine-active)** | 24.60 | 23.24 | 27.63 |
| **idle gap (trace wall − union)** | 4.17 | 5.22 | 4.50 |
| trace wall / token | 28.77 | 28.47 | 32.13 |

The summed family durations exceed the union by ~7.5–8.7 ms/token, i.e. work
overlapped on other streams; this is overlap, not idle.  Two independent
observations follow:

* **Expert GEMV is the single largest decode term** (42–54 % of the kernel
  union) and is dominated by reads of selected expert rows in place; there is no
  separate decode DMA (≤0.08 ms/token).
* **Decode attention/KV is negligible** (≈0.52 ms/token at every context,
  1.4–2.0 % of the union).  The 2K→128K decode slowdown is *not* a QSA/KV
  effect; GEMV and dense grow instead.

**Profiling perturbation.**  The matched unprofiled request's steady ms/token
was 28.78 (2K), 25.59 (32K), 35.34 (128K); the trace-internal wall per token was
28.77 (0 %), 28.47 (+11 %) and 32.13 (−9 %).  The profiler inflates the
*client-observed* stream badly (events are delayed and flushed late; e.g.
+268 ms/token client-side at 32K) but the trace-internal step wall stays within
the ±10 % run-to-run/thermal drift already seen across boots.  The family
ranking is stable across all three windows and matches the independent PP14
decode trace.

## 5. Routing and residency diagnostics

Direct per-token decode routing could **not** be measured on this stack and this
is recorded as a negative result.  The decode path is replayed by the breakable
CUDA graph, so Python in `MoeWNA16Method.apply` runs only during graph capture,
never during replay; a capture-time hook observes one fixed capture input and a
CPU copy inside capture aborts capture (observed:
`Cannot copy between CPU and CUDA tensors during CUDA graph capture`).  The
attempted `patches/decode_route_dump.py` is retained, capture-guarded, and
documented as unusable without disabling the decode graph.  The supported
in-graph route is SGLang's `enable_return_routed_experts` capturer, which
requires a diagnostic server-arg change and return plumbing that TG0 did not
run.

Reported separately, and clearly labelled:

* **Structural selection coverage** — presence placement keeps S=184 of 512
  experts per layer = **35.9 %** by count (the "process coverage").
* **Calibrated gate-weight mass** — presence placement covers 66.0 % of
  calibrated routing mass vs 84.3 % for mass placement (from the PP plan).  This
  is a *gate-weight* figure and must not be quoted as selection coverage.
* **Estimated host decode traffic** (estimate, not measured): with 10 selected
  experts × 48 layers = 480 expert reads/token and the PP6 measured per-expert
  GEMV row bytes (w13 0.819 MB qweight + 0.051 MB scales; w2 0.410 MB +
  0.026 MB = 1.306 MB/expert), host reads are **≈213 MB/token** if selection
  coverage matched the 66 % mass figure, up to **≈402 MB/token** if selections
  were uniform (35.9 % resident).  At the PP6-measured ~51 GB/s pinned-host read
  rate that is **≈4.2–7.9 ms/token**, a substantial part of the 13–17 ms/token
  GEMV term.  Actual count coverage and therefore the true traffic lie in this
  bracket and were not measured.

## 6. Validation harness

`tools/long_logprob_oracle.py` was hardened:

* `validate_row`/`validate_payload` require identical `prompt_ids` and
  `continuation_ids`, exactly `len(continuation_ids)` finite logprobs, and
  self-consistent metadata (`forced_prompt_tokens == prompt_tokens +
  continuation_tokens`, `server_prompt_tokens == prompt_tokens`).
* `forced_logprobs` now requires the exact `len(cont)+1` response shape instead
  of silently filtering `None` and shifting positions.
* `stats` raises `OracleValidationError` on missing/truncated/mismatched rows
  and returns per-token deltas; `check`/`compare` write `<name>.check.json` /
  `<name>.compare.json` with the retained per-token data.
* Measurement is separated from policy: `check`/`compare` report only and fail
  (exit 1) **only** when the caller passes `--fail-above T`.  The old hard-coded
  0.05 gate is removed because it fails the unchanged baseline itself (run-to-run
  max reaches 2.37, §7).

`tools/test_long_logprob_oracle.py` adds 20 focused CPU tests for
truncated/empty/extra/non-finite (`NaN`, `-inf`) logprobs, mismatched prompt and
continuation ids, metadata inconsistency, missing fields, and `stats` input
mismatch.  All 20 pass.  Re-running the hardened tool over the retained PP
artefacts reproduces the closure review's 2.797 at forced-token index 6,
confirming the hardening did not change the comparison.

## 7. Bounded PP14 diagnostic

`tools/tg_pp14_diag.py` took three accepted and three prefetch-off observations
of each existing long oracle prompt in balanced boot order (accepted, off, off,
accepted), with retained per-token comparisons.  Prefetch-on was restored by the
final accepted boot.  Per-run max |dlogprob|:

| Prompt | within accepted (3 runs) | within prefetch-off (3 runs) | cross-arm max | cross max index |
|---|---:|---:|---:|---:|
| canonical | 0.716 / 0.814 / **1.206** | 0.570 / 0.975 / 0.626 | 1.457 | 5–6,14 |
| long-2chunk | 1.183 / 1.263 / **2.262** | 0.357 / 2.109 / 2.140 | 2.377 | 5–6, other |
| long-4chunk | **2.374** / 1.436 / 1.486 | 0.691 / 0.710 / 0.907 | 1.875 | 6,8,13 |

The historical unresolved value (2.797, prefetch-off, long-2chunk) sits **inside
the accepted stack's own observed run-to-run range** (up to 2.374), at the same
early forced-token positions (index 5–6, where the fixed suffix token has
logprob ≈ −3 to −8.6 in both arms).  Both arms show comparable early-token
spread.  Conclusion: the 2.797 is an early-token run-to-run draw, not a
prefetch-path effect; a quieter repeat alone would not have shown this, but
matched repetitions across boots do.  This characterises variability — it does
**not** establish bit-exact equivalence, and long-prompt logprobs remain
non-deterministic by design.

## 8. Sustained decode-path numerical/state check

`tools/tg_numcheck.py` compares the per-step logprob of each greedily generated
token (actual incremental decode, `return_logprob`) against the logprob the same
token receives when the whole history is teacher-forced in one pass.  It is a
targeted state comparison, not a full per-kernel harness.

| Prefix tokens | crossing | 8192-ring cross | max \|dlogprob\| | mean |
|---:|---:|:---:|---:|---:|
| 2,048 (control) | 2,080 | no | 0.0147 | 0.00084 |
| 4,096 (control) | 4,128 | no | 0.0112 | 0.00045 |
| 8,180 code | 8,212 | yes | 0.3077 | 0.0198 |
| 8,192 code | 8,224 | yes | 0.3154 | 0.0144 |
| 8,180 prose | 8,212 | yes | 0.1281 | 0.0218 |

Crossing the `SGLANG_KV_TIERS_W=8192` ring raises incremental-vs-reprefill
max |dlogprob| by roughly 10–30× (0.011–0.015 → 0.128–0.315).  This directly
exercises the recurrent GDN state, the PLE path and the tiered KV ring at the
boundary.  **Coverage limits:** one sequence per case, code and prose only; it
does not verify every layer, the sampling kernel, or multiple concurrent
sequences, and it measures the incremental-vs-reprefill delta of this
configuration rather than a bit-exact reference.  The ring-boundary drift is
therefore a measured baseline characteristic that future promotions must bound,
not a proven bug.

## 9. Validation status and limitations

* Before any change is promoted, the long-prompt oracle must be treated as a
  **variability characterisation** with a baseline-derived policy, not a fixed
  0.05 gate.  The retained per-token data is the input to that policy.
* Per-token decode routing and therefore true decode selection coverage /
  traffic remain unmeasured (graph-replay gap).  Traffic numbers here are
  estimates and must not be quoted as measured bytes.
* The 8192-ring incremental/eager drift (up to 0.32) is a standing baseline
  anomaly; a correctness claim for a change that touches decode state beyond
  8192 needs a stronger, path-specific check than this harness provides.
* Profiling overhead cannot be resolved below ~±11 % because matched unprofiled
  requests themselves drift that much; profiled-vs-unprofiled comparisons must
  use the trace-internal step wall, and the client stream must not be used as a
  token-latency source while profiling.
* The capacity smoke and every long-context cell are single-boot observations.
  Reported free VRAM is sampled, not a guaranteed reserve.

## 10. Recommended next experiment (ranked, not executed)

**TG1: presence vs mass placement at fixed S184, measured on TG.**  Rationale:
expert GEMV is the largest decode term (12.96–17.13 ms/token, 42–54 % of the
kernel union) and is dominated by host-resident expert reads; the two placements
differ only in which experts are resident, and the PP plan's calibrated
gate-mass coverage is 66.0 % (presence) vs 84.3 % (mass).  If the mass placement
raises *selection-count* coverage toward its mass figure, host decode traffic
falls within the estimated 213–402 MB/token bracket.  **Estimated ceiling:**
≈8 % realistic and up to ~15–20 % optimistic single-stream TG if the host-read
share of GEMV is removed, with code the most likely beneficiary (it is the
slowest class today).  The experiment must hold PP flat (no reproducible >2 % PP
regression), use bracketed boots, and report every workload separately; the
66 % vs 84.3 % mass figures alone are not a speedup.
