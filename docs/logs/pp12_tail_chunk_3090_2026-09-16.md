# PP12 — tail-chunk staging amortization: ACCEPTED

Date: 2026-09-16. Host: RTX 3090, driver 580.178.04. Stack: accepted PP5c/PP11
state (bulk pread + 128 MiB recent-row cache, 2,048-byte gather tile, host-row
DMA staging + batching, S184, presence placement). The only functional variable
was `SGLANG_3090_CHUNKED_PREFILL_SIZE`; the launcher flag pass-through already
existed, so this was one environment variable per arm.

## Hypothesis

The canonical 4,565-token prompt runs as two 2,048-token chunks plus a 469-token
tail. Every layer-chunk re-stages its selected experts into the compact staging
buffer, and PP6 showed the tail still pays 664 of its 1,107 ms for staging: the
per-layer-chunk staging cost is fixed, not token-proportional. Processing the
prompt in fewer chunks should therefore cut the total staging.

## Method

Three fresh-server arms via `tools/capture_pp5b_arm.py --skip-heldout`
(one excluded plus five measured canonical requests, both oracles, GPU
telemetry, status, launcher/environment metadata, checksums), presence
placement, S184, one variable per restart:

| Arm | Chunk | Scope | Directory |
|---|---:|---|---|
| control A | 2,048 | discovered at runtime | [ctrl-a-2048](raw/pp_tail_chunk_3090_2026-09-16/ctrl-a-2048/) |
| variant | 4,608 | discovered at runtime | [var-4608](raw/pp_tail_chunk_3090_2026-09-16/var-4608/) |
| control B | 2,048 | discovered at runtime | [ctrl-b-2048](raw/pp_tail_chunk_3090_2026-09-16/ctrl-b-2048/) |

Chunk 4,608 makes the whole 4,565-token prompt a single extend; 2,048 makes
three. Only the exact active `sglang-*.scope` was stopped between arms.

## Result

Measured-only (warmup excluded):

| Arm | Chunk | Measured PP tok/s | Mean +/- sample SD | Decode mean |
|---|---:|---|---:|---:|
| control A | 2,048 | 1296 / 1296 / 1283 / 1289 / 1288 | 1290.4 +/- 5.6 | 42.3 |
| variant | 4,608 | 1943 / 1939 / 1916 / 1950 / 1941 | **1937.8 +/- 12.9** | 42.4 |
| control B | 2,048 | 1287 / 1275 / 1264 / 1286 / 1298 | 1282.0 +/- 12.9 | 42.9 |
| Pooled control | 2,048 | ten samples | 1286.2 +/- 10.4 | 42.6 |

The variant is **+651.6 tok/s, +50.66%** over pooled control (t = 98.3; the
smallest variant sample, 1916, exceeds the largest control sample, 1298).
Excluded warmup PP was 828 / 1214 / 859. Decode did not regress (42.4 versus
42.6 pooled).

## Exactness and safety

Both oracles are identical to the accepted baseline in all three arms:

```text
m4_3090_untuned: LOGPROB_MAX=0.000000 LOGPROB_MEAN=0.000000
lp2:             LOGPROB_MAX=0.168757 LOGPROB_MEAN=0.011632
```

Chunking only changes the prefill schedule; the per-expert math and fused kernels
are untouched, and the oracles confirm it.

Minimum free VRAM sampled during capture: 2,941 MiB (2048 arms) and
2,433 MiB (4,608) — lower because a larger chunk materializes more logits, but
still far above the 1.2 GiB operational floor. A separate long-prompt pass on a
4,608 server (bundled evidence under
[safety-4608](raw/pp_tail_chunk_3090_2026-09-16/safety-4608/)) ran 4,565 / 9,490
/ 20,315 / 29,272-token prompts with no OOM, retraction, traceback, or CUDA
fault; minimum free VRAM was 2,211 MiB.

## Verdict

**ACCEPTED.** Fewer, larger chunks amortize the fixed per-layer-chunk staging and
recover **+50.66%** warmed PP on the canonical code workload with unchanged
oracles and no decode regression. The launcher default is promoted from 2,048 to
4,608 with the existing helper:

```bash
python3 patches/enable_prefill_chunk_residency.py apply
```

The helper now forms a three-state ladder (pre-PP3 chunk 1024 -> PP3 chunk 2048
-> PP12 chunk 4608); `revert` steps back one rung. `SGLANG_3090_CHUNKED_PREFILL_SIZE`
still overrides at start time.

## Caveat

Chunk size is a global default, not a per-prompt one. A larger chunk raises the
per-request activation/logit footprint (about 0.5 GiB more on this workload) and
would hurt request interleaving on a multi-request server; this box runs
`--max-running-requests 1`, so that cost does not apply. The gain is the
chunk-count amortization, which also reduces chunk counts for longer prompts
(the 29,272-token pass ran as seven 4,608 chunks and was error-free).
