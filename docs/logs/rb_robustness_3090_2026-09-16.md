## 1. Reproducer

The RC1-d crash: 16 mamba slots, chunk 2048, 262,144 requested pool (profiled
to 187,200), 30 unique ~6.6K conversations cold+warm (~199K retained tokens),
then evict/rehit with 50 fillers. Unpatched, the server died at ~139K backed
tokens (`rc1 chunk_arms/c2048/server.log:25325`).

## 2. Attempt 1 (flags on, `r123_slots16_c2048/`) — failed, informative

Died on the **first** request. Two defects in the patches, both fixed:

- R3 used the existing watermark's half-headroom (768 MB). With 16 slots this
  box idles at ~765 MB driver-free by design, so the first 10K commit was
  refused. R3 now uses an absolute floor `SGLANG_KV_LAZY_MIN_FREE_MB`
  (default 256).
- The refusal landed on a *continuing 2048-token chunk* (committed KV), which
  R2 v1 declined to roll back and re-raised. R2 v2 releases such requests via
  `release_kv_cache(req, tree_cache, is_insert=False)`.
- R1 correctly did nothing: the tree was empty (all pages locked by the
  running chunked request), nothing to evict.

## 3. Attempt 2 (`r123v2_slots16_c2048/`) — passed

| check | result |
|---|---|
| long cold 7.2K / 21.7K / 36.2K | ok (1,036 / 1,674 / 1,698 tok/s) |
| churn 30 × 2 (~199K retained on 187K pool) | 30/30 cold, 30/30 warm hits, min free VRAM 78 MiB, **no crash** |
| evict/rehit (12 short, then 50 × 6.6K = 333K tokens) | a1 hit 6,592; a2 miss after pool overflow; a3 rehit 6,592 in 0.54 s |
| `OutOfMemory` / `Traceback` in server log | **0** |

Attribution from `server.log`:

| event | count |
|---|---:|
| R3 `strict headroom refused` (commit would leave < 256 MB) | 38 |
| R1 `KV physical pressure: evicted … retried allocation … -> ok` | 38 / 38 |
| R2 `aborting … request(s)` | 0 (never needed) |

Lazy backing plateaued at ~104K tokens / 720 MB with driver-free ≥ 0.82 GB at
commit time, versus growth to 139K / 960 MB and 0.00 GB free unpatched. The
tree evicted LRU prefixes (8,448 tokens per event) instead of the server dying.

## 4.1 Flags on the promoted profile (RC4′ checks), attempts 1–2

Goal: show R1–R3 are inert for the single linear session so the flags can be
promoted. Profile = promoted (4 slots, 235,520 pool/context, chunk 4608)
via the experimental launcher with flags on.

- Attempt 1 (`r123_on_promoted_profile/`): my 225K probe prompt overshot the
  context (237,840 > 235,520) and was rejected at admission with HTTP 400 —
  correct behaviour, 0 errors, but the probe tool aborted. Tool fixed
  (over-length depths are recorded as rejected).
- Attempt 2 (`r123_on_promoted_profile_v2/`, floor 256 MB):
  - TG probe: 28,440 tokens hit → TTFT 1.03 s, TG 30.24 tok/s; 123,750 hit →
    TTFT 0.55 s, TG 30.40 tok/s. Same as flags-off (RC4′ / promoted boot).
  - The 215K cold prime was **refused by R3 at 163,840 tokens (free 213 MB
    < 256 MB floor)**; `full_evictable_size_=0` so R1 had nothing to evict;
    **R2 aborted the request with HTTP 503 and the server kept serving**
    (later requests 200, graceful stop by the driver, 0 tracebacks). **R2 is
    therefore validated.**
  - A second refusal followed for a 6K request at 180,224 tokens: after the
    abort the allocator kept handing out never-backed high-index pages because
    R1 only re-sorted the free list on eviction. R1 v2 now re-sorts and
    retries *before* considering eviction.
  - Finding: a 256 MB floor is incompatible with this profile's near-limit —
    unpatched, the 4-slot profile runs its last ~60K tokens at 30–100 MiB
    free (RC1-e reached 247K), and RC1-d's activation OOM occurred at 33 MiB.
    The floor is now a launcher setting; attempt 3 uses
    `SGLANG_KV_LAZY_MIN_FREE_MB=64`.

- Attempt 3 (`r123_on_promoted_profile_v3/`, R1 v2, floor 64 MB): **no
  crash** (0 tracebacks, 0 SIGQUIT; R2 fired twice, R1 evicted once when
  session B displaced A). TG 30.5 / 30.1 tok/s and TTFT 0.41 / 0.54 s at 28K /
  124K; B 20/20; 12-turn trace 12/12. But R3 still refused the sole request
  at the near-limit: the 215K prime at ~170K with 55 MB free, and session A at
  turn 50 (~180K) with 77 MB free — `full_evictable_size_=0` both times. A
  linear session was therefore capped at ~180K instead of the 247K the
  unpatched profile reaches.
- Design change (attempt 4): the floor exists to stop *retention-driven*
  growth, not a sole request growing into its own margin. R1 v3 now, when
  nothing is evictable, sets `_strict_bypass` on the pool for one retry so
  R3 lets the commit through — identical to the unpatched behaviour for a
  single session — while retained pages still trigger eviction first.
  Serving diff `47ef80c2...`.
- **Attempt 4 (`r123_on_promoted_profile_v4/`, R1 v3 + bypass, floor 64 MB)
  — passed.** 0 tracebacks; the only SIGQUIT lines are the driver's normal
  shutdown at the end.

  | check | flags on (v4) | flags off (RC4′ / RC1-e) |
  |---|---|---|
  | TG at 29K / 126K / 215K (hit) | 31.3 / 30.5 / 29.7 tok/s | 35.7 / 35.0 / 34.3 (RC4′) → 30.8 (promoted boot) |
  | TTFT warm at those depths | 0.58 / 0.63 / 0.53 s | 1.04 / 0.50 / 0.71 s |
  | 215K cold prime | served, 96.8 s | 112 s at 249K |
  | session A | 64/64 hits to 231,310, warm median 2.26 s | 70/70 to 247,228 (262K pool) |
  | session B after A, no flush | 20/20 | 20/20 |
  | 12-turn trace | 12/12, median 1.95 s | 12/12, 1.86 s |

  Log attribution: R3 refused twice (both on the 215K prime), R1's re-sort
  retry did not suffice, and the sole-owner **bypass fired once → ok**; R1
  evicted 0 times (B's growth stayed above the floor), R2 aborted 0
  requests. The flags are inert for the linear session except for that one
  bypass, which reproduces the unpatched behaviour.
